# Knowledge UI

[Feature index](README.md) · [German navigation guide](../guides/knowledge-ui.de.md) · [Knowledge model proposal](../architecture/knowledge-catalog-migration.md)

## Status and objective

**Implemented.** The knowledge workspace replaces the long category navigation with four
topic areas: **Grundlagen**, **BodyGraph**, **Variablen** and
**Inkarnationskreuze**. A topic contains categories; a category contains individual
entities. Neither every category nor every entity gets its own top-level tab.

`app/templates/base.html` exposes one Wissen link. `/knowledge` provides the
topic/category/entry workspace. The previous catalogs remain available with the
shared navigation and their original entry anchors. Center-timeline help is at
`/knowledge/help#center-timeline`; its old `/knowledge#center-timeline` anchor is
retained in expandable help on the default page.
The structured HD vocabulary exists, but the unified multilingual storage model
is still a separate proposal. This navigation does not depend on that migration.

## Information architecture

The existing database categories retain their identities. Topic membership is
presentation metadata, not a change to entity structure or calculation results.
Every category has one primary topic; related links can cross topic boundaries.

| Topic / stable UI key | Category labels shown in the UI | Existing category keys or source |
|---|---|---|
| Grundlagen / `basics` | Typen, Strategien, Signaturen, Nicht-Selbst-Themen, Aura, Autoritäten, Profile, Himmelskörper, Persönlichkeit und Design | `type`, `strategy`, `signature`, `not-self`, `aura`, `authority`, `profile`, `body`, `source` |
| BodyGraph / `bodygraph` | Zentren, Definition, Tore, Kanäle, Schaltkreise, Linien, Torlinien | `center`, `definition`, existing `Gate`, `Channel`, `Circuit` catalogs, `line`, `gate-line` |
| Variablen / `variables` | Variablen, Pfeilrichtungen, Color, Tone, Base, Determination / Verdauung, Umgebung, Perspektive, Motivation, Kognition | `variable`, `direction`, `color`, `tone`, `base`, `digestion`, `environment`, `perspective`, `motivation`, `cognition` |
| Inkarnationskreuze / `crosses` | Kreuz-Geometrie, Erfasste Inkarnationskreuze | `cross-angle`, `cross` |

Profiles in Grundlagen means the twelve HD profile concepts, not saved personal
birth profiles. Those remain in the main application's Geburtsprofile section.
The center catalog belongs to BodyGraph; the personal Zentren-Verlauf remains an
analysis tool outside the knowledge catalog.

Himmelskörper offers access to both the structured `body` entries and the existing
symbolism page. Keep their source and context distinct; do not silently merge or
overwrite their text before the knowledge-model migration.

## Navigation and layout

The main sidebar has one **Wissen** entry leading to `/knowledge`. Within that
workspace, show four topic links styled as tabs, followed by category navigation
and the selected category's entries. `/knowledge` starts at Grundlagen / Typen.

```text
Wissen
[Grundlagen] [BodyGraph] [Variablen] [Inkarnationskreuze]

BodyGraph > Tore

Categories          Entries                    Selected entry
Zentren             Tor 1                      Name and stable ID
Definition          Tor 2                      Structure and relationships
Tore (selected)     ...                        Description and provenance
Kanäle
Schaltkreise
Linien

```

This is a conceptual layout, not three permanently visible columns.
The implementation uses wrapping topic, category and entry links above the
selected detail. Narrow screens stack them; topic links wrap without page
overflow or rely on hover. Preserve the existing specialized gate/channel
visualizations instead of forcing them into a plain-text detail card.

Selecting a topic without a category opens its first category in the table's
order. Selecting a category without an entity shows its entry list and an explicit
selection prompt, rather than arbitrarily opening the first entity. A topic
introduction should be short and never displace the actual catalog navigation.

## State and links

Canonical route:

```text
/knowledge?area=bodygraph&category=gate&entity=gate.1
```

`area`, `category` and `entity` describe the navigation state. `gate`, `channel`
and `circuit` are UI category keys for the existing specialized catalogs, not
new `HdEntity` database categories. Presentation IDs such as `gate.1`
map to existing records and do not require a new identity table.
Preserve current HD IDs exactly.

Use ordinary server-rendered links with `aria-current="page"`; the visual tabs
are navigation, not an ARIA tab widget. Basic browsing, direct links and browser
Back/Forward work without JavaScript. Optional filtering may enhance this later,
but is not required for the first release.

The URL is the state source, with no separate local-storage selection.
Validate that the category belongs to the topic and the entity belongs to the
category. Unknown or contradictory values return an explicit 404; do not silently
substitute a default. Defaults apply only to omitted selections. If a category
alone is supplied, infer its primary topic; an entity selection requires its category.

Keep `/gates`, `/channels`, `/knowledge/celestial-bodies` and
`/knowledge/entities?category=…`, including existing entry anchors, reachable.
They may continue rendering specialized views with the shared knowledge
navigation. Update chart/catalog links to expose the correct topic and category,
while preserving their precise entry targets. Do not redirect old fragments into
an incompatible detail layout.

## Lists, details and relationships

The workspace avoids rendering all 384 gate-line descriptions as one long page. Torlinien first
asks for a gate, then offers its six lines; general Linien remains a separate
category. The legacy entity route retains all entry anchors for compatibility.
The optional `gate=10` parameter selects a gate before an individual line;
an exact gate-line ID also selects its gate. Contradictory gate/line selections
return 404. Gate numbers and line numbers sort numerically, not lexicographically.
Channels use their gate pair; other categories use an explicit domain order
where available. Names are display text, never lookup keys.

A generic entry detail shows its name, stable ID, readable structural facts,
description and per-entry text provenance. Raw JSON can remain a secondary
technical detail, not the primary explanation. Show only relationships present
in authoritative catalog data, including gate/center, channel/gates and
channel/circuit links. Do not invent inferred interpretations to fill the UI.

Keep **KI text origin**, **human text origin** and **review state** distinct:
an AI-origin text marked reviewed is still AI-origin. Display author, model
when applicable, date and review status. A missing description says
“Noch kein Beschreibungstext”; the structural entity remains navigable.

Erfasste Inkarnationskreuze is not advertised as a complete directory. Display
the stored angle and the four gates in personality Sun/Earth, design Sun/Earth
order. An empty cross catalog is a valid empty state, not a database failure.

Knowledge browsing does not require a selected birth profile and does not trigger
chart calculations. In the new gate workspace, optional profile highlighting is
off initially; explicitly enabling it loads natal activations and may calculate
missing data via the existing overlay endpoint. The legacy gate page keeps its
previous enabled-by-default behavior. There is no implicit transit/natal synthesis.

## Errors, accessibility and scope

Distinguish a valid empty category, a missing description and unavailable catalog
storage. Keep existing explicit migration/database errors; never show an empty
success-shaped catalog when loading fails.

Use labeled navigation landmarks, logical headings, visible keyboard focus and
textual selected-state indicators. Keep text provenance and warnings visible
without color alone. Cross-topic links must indicate their destination.

Move the existing center-timeline explanation into linked application help
without losing its content; it is not an entity category. Keep the general
interpretive-system warning and specific limitations around digestion,
environment and cognition. Catalog labels are not health or lifestyle advice.

The first release changes navigation and presentation only. It does not add text
editing, global search, translations, new entity types or automatic
interpretations. Localization and unified storage follow the separate
[knowledge model proposal](../architecture/knowledge-catalog-migration.md).

## Implementation and acceptance

The topic mapping and URL helpers live in `app/knowledge.py`; route selection is
in `app/main.py`. Shared navigation and entry selection are server-rendered
template partials. `tests/test_knowledge.py` covers the workspace alongside
existing catalog and chart regression tests. The following requirements guide
future changes:

1. Define one ordered UI topic/category mapping, reusing `CATEGORY_LABELS` for
   existing HD labels. Verify that all current keys are covered exactly once;
   an unmapped future category must surface a configuration error.
2. Add validated URL selection and shared navigation in `app/main.py` and the
   knowledge templates. Reuse existing catalog reads and gate/channel components.
3. Wire the sidebar, old catalog pages and chart entry links to the same topic
   selection. Add responsive layout using the existing stylesheet.
4. Add focused route/rendering tests and check keyboard and narrow-screen use.

Acceptance requires exactly four topic links; coverage of all current HD categories
plus gates/channels/circuits; accurate active navigation for direct and old links;
404 responses for invalid selections; distinct empty/missing/error states;
numeric gate-line ordering with six selectable lines per gate; preserved
catalog relationships, provenance and profile highlighting; browsing without
JavaScript or chart-service requests; and no horizontal page overflow at a
320 CSS-pixel viewport.
